# Quality 最小實作契約

本契約承接重建計畫的步驟二，供步驟三製作代表案例。來源、因素、資料、狀態、操作、路徑與場次各自有責任，透過固定識別碼連接。這是第一版候選，尚未實作通用執行器，也未啟用測試 Skills。

機械可讀欄位與列舉值位於 [minimum_contract.yaml](minimum_contract.yaml)。

## 成果與責任

| 成果 | 維護者責任 | 本步狀態 |
| --- | --- | --- |
| `sources.yaml` | 盤點全部來源，保留原文、要求與缺口 | 已建立第一版 |
| `factors/` | 依要求與必要情境建立獨立可判定結果 | 步驟三開始 |
| `execution/` | 定義資料、可解析狀態及有來源的操作 | 步驟三開始 |
| `routes/` | 固定因素全集後安排有效檢查位置 | 步驟三開始 |
| `generated/` | 從來源定義產生閱讀版，不另寫預期結果 | 步驟三開始 |
| 場次目錄 | 保存版本、操作、逐項結果、證據與清理 | 尚未建立真實場次 |

產品預期只能來自已鎖定來源。平台負責定位、操作、觀察與等待，不能修改產品通過標準。來源矛盾由來源主人處理，Quality 保留衝突與影響範圍。

## 來源與要求如何連接

來源索引包含六種來源 Git。三個 Spec Git 完整列舉已追蹤檔案，其餘 Git 僅鎖定本次指定文件。每份來源保留相對路徑、Git commit、blob 與 SHA-256。工作指令及 Git 設定另列排除理由，沒有從檔案數中消失。

每份來源下有原文章節區塊與節點。區塊保留全文，節點保留摘錄及行號。節點的祖先引用保留條件、元素及互動。`ELSE` 的對應分支、同操作的共用條件與提前返回規則，必須連同整個區塊解讀，不能只讀最後一行。

| 欄位 | 意義 |
| --- | --- |
| `sources[].id` | 文件身分，不隨行號或改名變動 |
| `contexts[]` | 原文標題階層、完整區塊及行範圍 |
| `nodes[].id` | 原文段落、條列、圖或資料集合的身分 |
| `kind` | 要求、元素、資料、狀態、互動、共用規則、上下文或線框 |
| `disposition` | 驗證要求、操作依據或有理由的範圍外內容 |
| `claims[]` | 從節點拆出的要求。可分別出錯的結果分列，仍共用原句與條件 |
| `claims[].status` | 尚待因素或存在來源缺口，不表示實跑結果 |
| `gap_refs` | 直接影響這項要求的來源缺口 |
| `references[]` | 跨文件操作、共用政策、模型與上游來源的引用 |

同一要求可同時提供操作依據。`requirement` 的節點不因用於準備步驟就從覆蓋分母移除。輸入、條件及適用列表單獨作 `basis`，必須與其行為結果共同使用。線框和原始範例保留為依據，發現與正文衝突時列缺口。

語系設定的一句排序規格已拆成進入時目前項目置頂、其餘項目初始排序、改選後保持順序三項。代碼搜尋與原生名稱搜尋分列。搜尋各自需要包含符合項與排除不符合項的因素，這些因素在下一步建立。

本版要求數不是最終因素數。後續仍需從每項要求展開必要條件、邊界與失敗情境。拆分或合併要求時記錄舊識別碼與替代關係，不能因代表案例沒有用到而刪除要求。

來源缺口以 `open` 與 `resolved` 區分。只有修訂內容已納入可取回的鎖定來源，才在該版索引標為 `resolved` 並解除要求的缺口引用。已取得決策但尚未更新鎖定來源時，原版缺口仍為 `open`，不能解讀為使用者尚未決定。移除或拆分的識別碼以 `retired_ids` 保存原識別碼、替代識別碼及理由，替代目標必須存在。

## 識別、引用與版本

| 前綴 | 對象 |
| --- | --- |
| `SRC-`、`CTX-`、`N-`、`R-` | 來源、原文區塊、節點與要求 |
| `F-` | 因素 |
| `D-`、`S-`、`A-` | 資料、狀態與操作 |
| `RT-`、`B-` | 路徑與執行時比較基準 |
| `GAP-`、`REP-` | 來源缺口與代表案例 |

識別碼在同一份 Quality 定義集合內唯一。引用保存完整識別碼，不能靠同名檔案、清單位置或行號識別。首次建立時的流水號只是編號，修改文件後不能重新編號。

來源取回使用鎖定提交，不使用浮動 `main` 的內容。

```bash
git -C "$SOURCE_REPO" show "$SOURCE_COMMIT:$SOURCE_PATH" > "$OUTPUT_FILE"
shasum -a 256 "$OUTPUT_FILE"
```

`SOURCE_REPO` 由索引的 remote 身分與本機 checkout 對應。取回後同時核對 blob 與 SHA-256。若另一台機沒有該提交，先由指定 remote 取得，取回失敗就是來源缺口。單有雜湊不能替代原文。

場次另鎖 Quality 定義與實際受測內容。已提交候選保存 commit、tree 與檔案雜湊。未提交候選需保存可完整取回的定義快照及逐檔雜湊，不得只記分支。App 組建與部署的後端版本獨立辨識。

來源改變時先判定語意影響，再追蹤要求、因素、資料、操作與路徑。舊場次保留舊版本，不能用新定義改寫舊結果。純文字整理可保留身分，但仍要更新內容雜湊並重建閱讀版。

## 因素、資料與狀態

因素的最小單位是在一個明確情境、有效檢查時點下，可以獨立判定的結果。每項因素必須有要求引用、成立條件、時點、預期與證據需求。勾選標記與列表保序會分別出錯，因此各自判定。

測試資料記錄來源允許範圍、具體值或可重建配方、選取理由、資料隔離及清理。帳號與資料集必須為本場次可辨識且獲准使用的測試資料。不能因準備方便就直接改寫受測結果，跳過本來要驗證的公開操作。

狀態條件使用可解析運算樹，不使用任意程式字串。運算子限於契約列舉的 `all`、`any`、`not`、比較、集合包含、集合相等、順序相等與存在判斷。

| 運算元 | 來源 |
| --- | --- |
| `literal` | 契約明示的常值 |
| `data` | 路徑綁定的資料值 |
| `fact` | 由平台觀察或操作紀錄取得的事實 |
| `baseline` | 同場次已取得且仍有效的比較基準 |

`data` 與 `baseline` 的名稱是路徑宣告的綁定名稱。綁定必須唯一解析到 `D-` 或 `B-` 識別碼與欄位。`fact` 名稱必須先在能力交接中宣告型別、取得方法與有效範圍，不允許臨時猜測欄位。例如 `entry.complete_order` 可作具名基準綁定，不是全域常值。

事實必須帶型別、觀察時間、事件、證據與範圍。範圍至少能分辨場次、嘗試、受測版本、畫面訪次與資料集。離開畫面後重進，不得沿用同一次進入的順序基準。

條件結果為 `true`、`false` 或 `unknown`。缺值、過期觀察與無法取得的證據均為 `unknown`，不能轉成 `false` 或通過。明確觀察到不存在才可令 `exists` 為 `false`。已知 `null` 與尚未觀察是不同狀態。型別不相容屬無效定義，開始前受阻。

集合比較不能自行轉換大小寫、排序或去重。完整列表順序用 `sequence_eq`，僅有畫面局部截圖不足以支持此判定。

## 操作完成與產品結果

操作記錄目標、資料、前提、展開步驟、完成訊號、能力與成本。完成訊號來自工具回應或可取得觀察的時點，不能以預期結果出現作為唯一結束條件。

例如點按 English 後，操作可記錄已送出且工具已回應。平台接著取得畫面與完整列表。English 有沒有勾選、列表是否保持原順序，分別交由因素判定，不能先寫成操作後已成立的狀態。

`expected_after` 只描述預期。後續步驟的前提要重新用實際觀察判斷。標記失敗但頁面仍可操作時，可以繼續檢查保序與下一次改選。頁面不存在時，才阻擋依賴該頁面的步驟。

操作等待上限是平台執行設定。若 Spec 沒有產品時限，工具逾時不能直接判產品失敗。應區分操作未能開始、已操作但缺觀察，以及已取得不符合預期的充分證據。

## 路徑與產生文件

路徑先固定因素全集，再安排起點、操作、比較基準、檢查位置、續作與清理。每個因素都要有可到達的條件與時點。同一操作可以承載多個檢查，但各項仍獨立記錄結果。

每個步驟具有自己的識別碼。檢查要指出因素、時點、取得的觀察與必要證據。基準必須先取得才可引用，且只能用於其有效訪次與資料版本。準備、定位、捲動、輸入、導航、觀察、等待、恢復與清理均計入成本。未知成本為 `null` 並附理由，不能填零。

覆蓋分成三組，分母各自固定。

- 要求是否有必要因素。從完整 `sources.yaml` 反查，包含來源缺口與尚待因素。
- 因素是否有有效路徑。從已固定因素全集反查，不因無法安排而移除。
- 選定因素的實際判定。由場次結果彙整，不能以規劃覆蓋代替。

閱讀文件只展開來源與定義。產生器記錄版本、輸入雜湊與定義鎖定。改變來源或定義後重建相依閱讀版。最小契約與 README 由人維護，操作表、覆蓋報告與場次報告由機械來源產生。

本步的 `scripts/check_sources.py` 只核對來源索引、最小契約欄位與代表案例引用。它不拆因素、不求路徑，也不提供平台操作或通用測試方法。可重複使用的工具仍待步驟四萃取。

檢查器使用 Python 3 與 Ruby 標準 YAML 解析器，只讀取 Git 來源，不連線、不執行產品測試。以下命令在 Quality 工作區執行。

```bash
python3 scripts/check_sources.py
```

另一台機的 checkout 位置不同時，可重複使用 `--repo id=path` 指定來源位置。來源身分仍以索引的 remote 與 commit 核對。

## 五種結果與重跑

| 判定 | 成立條件 | 必須留下的內容 |
| --- | --- | --- |
| `pass` 通過 | 條件與時點有效，證據完整，預期為真 | 實際觀察與證據引用 |
| `fail` 失敗 | 條件與時點有效，證據完整，預期為假 | 不符合內容及其證據 |
| `blocked` 受阻 | 已確認前提或能力缺失，無法開始或繼續檢查 | 缺失項與真正受影響因素 |
| `inconclusive` 證據不足 | 已操作，但觀察、基準或紀錄不足以判定 | 已做操作、缺什麼及是否能補觀察 |
| `not_run` 未執行 | 尚未檢查，也沒有已確認阻礙 | 保留於選集與統計分母 |

每次嘗試保留時間、操作事件、實際條件、檢查時點、觀察、基準、判定與證據雜湊。可於原有效時點補足觀察時追加紀錄，不能覆蓋原始證據。時點已過就重跑相依步驟，留下新嘗試。

摘要使用同一場次、同一鎖定版本下，嘗試編號最大的有效結果。仍須列出先前失敗與重跑原因，不能只保留最後成功。版本改變或證據到期使結果不再有效時，保留原判定並記效力變更，不能改成通過。

清理結果獨立記錄為待處理、完成、失敗或不適用。清理失敗不抹除產品因素結果，但必須阻止宣稱環境已恢復。

## 場次保存、續作與到期

本版預設場次根目錄為 `~/Doc/quality_runs/susugigi/no2_accounting_app`。它位於 Quality Git 之外，不能落在任何 Git checkout 或暫存目錄。這是待實跑時建立的設定，本步未建立資料夾或真實場次。

場次編號使用 UTC 時間與八碼隨機識別。每個目錄保存 `manifest.yaml`、`results.yaml`、`report.md` 與 `evidence/`。證據路徑必須位於該場次內，拒絕跨目錄跳轉與逃逸符號連結。具體本機路徑記在場次 manifest，不放進可移植的產品定義。

保存期為結束後 30 天。中斷場次從最後活動時間計算 30 天，但未解失敗、中斷與未完成清理都標記保留，禁止自動刪除。實跑前必須填入具體到期時間、可寫位置、容量與隔離資料設定。

到期時標記待檢視，停止以已失效證據支持目前結論。需要延長時記錄新到期日及原因。需要移除時先列出具體場次與資料損失，依既有授權政策取得對應刪除授權，刪除收據保存於場次外。到期本身不是刪除授權。

續作時重新核對來源、定義、受測內容、環境、資料與目前狀態。鎖定內容未變且觀察範圍有效，才在同場次新增嘗試。任一鎖定內容改變時另開場次，透過 `resumed_from` 指向前次。不能把舊畫面、舊資料或另一台機的未驗起點當成目前狀態。

## 本步驗收邊界

來源取回、逐檔雜湊、內容摘錄、全集列舉與引用可以機械核對。要求拆解、共同條件、缺口影響與案例理由仍須回查原文審讀。檢查器通過不代表全部產品情境已有因素。

本步完成後，代表案例可開始製作定義。實跑仍需有效因素、路徑、候選版本、觀察能力與平台交接。iOS 維持由 `test-ios` 管理，舊測試格式與已停用方法不因本契約完成而恢復。
