# R15 本機 StoreKit 購買與到期

操作依 [12 項測試步驟](no17_r15_user_steps.md)。本文件持有準備、取證與清理方法，CSV 保留對應的單一步驟。

本次誰準備、誰操作、誰取證及哪些畫面需停下觀看，由鎖定 Control 的執行分工安排。test-ios 持有環境、商店設定、受控重開與清理生命週期。換人操作不改變判定或必要證據。

- **涵蓋測項:** PM-06、PM-07、PM-08、PM-09
- **前置場次:** 無
- **caseId:** `R15`
- **runtime_route:** `simulator`
- **driver:** `sim-review`
- **起點狀態:** 獨立 QA session。App 使用繁體中文，停在設定頁。本機商店沒有有效訂閱，購買錯誤設定已關閉，App 為免費版。
- **終點狀態:** 各項功能判定已完成。本場商店、測試設定、資料與 QA 身分完成清理，清理結果分開記錄。
- **前置環境:**
    - iOS Simulator 與 Xcode 本機 StoreKit，不需切換 Apple 帳號。
    - 每輪核對候選、建置產物及安裝產物的商店設定雜湊。
    - QA App 消耗有效 proof 後，以 SKTestSession 啟用商店。每次 open-app 均須取得原生啟用標記。
    - 沿用 canonical QA Firebase、QA bundle、拋棄式匿名身分與 READY 對帳。
    - test-ios 管理單一 Simulator、主 checkout build、Metro 與清理。
- **fixture 引用:** [R15 本機商店資料](no1_fixtures.md#r15-本機商店資料)，商品來源為候選 Impl 的 `ios/SwishLocal.storekit`。
- **預估時長:** 約 60 分鐘，依操作及觀看安排調整。
- **步驟表:** `no17_r15_local_storekit.csv`

## 環境準備

沿用 [受控執行入口](control_adapter/ios_runbook.md)。鎖定 Impl、Quality 與 Control 候選，以及商店雜湊、QA bundle 和 Simulator。

專用 scheme `SuSuGiGiApp-QA-StoreKit` 可用於編輯設定。受控執行使用 `SuSuGiGiApp-QA` 的 `Debug-QA`，由 SKTestSession 載入相同設定。兩個商品代碼必須符合 Impl 的 `PRODUCT_IDS`。

交接 UI 前須同時具備以下證據。

- 同次 open-app 的 READY 及 `QA NATIVE LOCAL_STOREKIT_READY`。
- 商店狀態顯示沒有有效訂閱，且購買錯誤設定已關閉。
- 設定頁可見「升級至 Premium」。

只選 scheme、build 成功、價格相符或 App 顯示已訂閱，都不能單獨證明商店已啟用。

## 共用資料準備

第 1 至 4 項不要求建立帳目。第 5 項前透過 App UI 建立 [R15 資料](no1_fixtures.md#r15-本機商店資料)。

1. 在設定 → 管理帳戶，把本場預設現金改為錢包、信用卡改為銀行，再新增 TWD 帳戶備用。
2. 在設定 → 管理類別，保留五個預設類別，再新增支出類別娛樂及醫療。
3. 從首頁新增基準支出 100 及錢包轉銀行 200。日期、備註與各欄位依資料表。
4. 核對 3 個帳戶、7 個類別、1 筆支出、1 筆轉帳及每個帳戶餘額，再交接第 5 項。

這是獨立場次，不使用 R02 的 JPY 帳戶或九筆交易。準備途中若已有非本場資料，先停止相依步驟並重新確認候選與身分，不清除個人帳目。

每次資料比對都以首頁及帳戶、類別列表核對。需要完整紀錄時將首頁期間切為「全」，展開所需分類。紀錄及餘額的必要畫面留在本次 session。

## 商店控制

Simulator 開發選單提供下列入口。每次操作均由原生端重驗同一 QA proof，完成後關閉結果提示再交接 App 畫面。

| 目的 | 開發選單項目 | 完成條件 |
| --- | --- | --- |
| 核對有效交易 | StoreKit：查看模擬購買紀錄 | 取得商品代碼、有效狀態與到期資料。 |
| 準備下一次獨立購買 | StoreKit：清除模擬購買紀錄 | 購買紀錄清空。讓 App 進背景後返回，設定頁重新出現升級入口，帳目不變。 |
| 模擬購買錯誤 | StoreKit：讓下一次購買失敗 | 取得設定成功結果。測完仍明確恢復正常購買。 |
| 關閉購買錯誤 | StoreKit：恢復正常購買 | 錯誤設定已關閉，可繼續下一項。 |
| 準備還原購買 | StoreKit：建立月費購買供還原測試 | 月費交易有效，並保留可點按的還原畫面。 |
| 排程月費到期 | StoreKit：10 秒後讓月費到期 | 取得排程成功結果，立即交接進背景。 |

只重設本場商店，不清除 App 帳目或 QA 身分。清除購買紀錄不算到期證據。

## 還原成功前置

先清除本場模擬購買，讓 App 回到免費，再從設定開啟升級頁。保留該頁，透過開發選單建立一筆有效月費交易。

開始第 7 項前，同時核對有效交易與「還原購買」仍可點按。實際點按須發生在該次還原查詢之前。若升級頁已被自動恢復關閉，該分支保持未驗，不以重裝、清帳目或指定 Premium 等級強造入口。

## 到期交接

第 8、9、11 項各自取得以下證據，不共用舊到期結果。

1. 保留到期前的有效月費交易及資料基準。
2. 排程十秒後到期，立即將 Swish 放到背景。十秒是本場控制設定，不是產品效能標準。
3. 取得 `QA NATIVE LOCAL_STOREKIT_EXPIRED`，並核對交易到期時間及沒有其他有效訂閱。
4. 確認完成後，才從 Simulator 主畫面點 Swish 回到仍存活的 App。
5. 核對設定頁的升級入口及該項資料。

查詢錯誤與沒有有效訂閱分開記錄。查詢失敗時不能把維持既有等級判為到期失敗，也不能在缺少到期證據時判通過。

## 完全關閉後重開

第 5、6、8 項由受控 runner 執行 cold-reopen，沿用同 session 並建立新的 open-app requestId。重新核對 READY、LOCAL_STOREKIT_READY 及商店交易狀態後，才交接畫面檢查。

點 App icon 只用於前一節仍在背景的程序。完全關閉後不可用無 QA launch arguments 的 icon 啟動代替受控重開。

## 證據與判定

- PM-06 的價格、取消、失敗各自判定。
- PM-07 的月費、年費各有購買及重開證據。兩者齊全才收下兩種訂閱自動恢復的檢查點。
- PM-08 的查無與成功各自判定，成功必須保留實際點按。
- PM-09 的 4 帳戶與 8 類別、4 帳戶與 7 類別、3 帳戶與 8 類別，都需分別測支出及轉帳。
- 停用後仍被限制與刪除後恢復新增，兩段都須取得證據。
- 執行結果只留 session，不記錄 token 或 raw Firebase uid。
- 本機 Xcode 簽章不作 Apple 簽章驗證依據。CF-01、CF-02、後端登記、伺服器通知及 TestFlight 帳號行為不在本場通過範圍。
- 缺少分支時回報 partial，逐項列出未驗內容。

## 還原

完成本輪操作、取證及已安排的觀看後，沿用受控 runner 收尾。

只清理本場專用 Simulator 的本機 StoreKit 交易，恢復錯誤設定與續訂速率。沿用本場 QA session 完成資料清理及 Auth disposal，獨立核對 `QA NATIVE LOCAL_STOREKIT_CLEANED`、Firestore cleanup 與身分移除結果，最後停止 Metro。

任一失敗均保留失敗結果。StoreKit 清理失敗保留 disposing proof，供同場重試。不得用刪除 App 或 erase Simulator 代替清理。保留給後續項目的資料，在整場結束前不提早刪除。
