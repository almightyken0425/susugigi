# 測試步驟撰寫方法

測項要讓接手的人或 AI 知道從哪裡開始、實際做什麼，以及如何判斷結果。操作分配依本次能力與使用者偏好安排。

撰寫時使用[內容範本](test_step_template.md)。改寫既有測項時可對照[改寫範例](test_step_examples.md)。六項資訊都必須明確，但可以沿用既有欄位，不必重複建立六組標題。

## 1. 說清楚要證明什麼

標題直接描述情境與結果，例如「取消購買後仍維持免費版」。目的說明這項測試能證明的行為及適用範圍。

購買成功、取消、失敗、還原及到期分開寫步驟與判定。需要沿用同一份資料時，可以放在同一場次，保留各自的結果。月費與年費若都在範圍內，兩種方案都要有明確判定。

不要把本機模擬商店的通過結果延伸成正式商店或後端流程通過。

## 2. 寫出具體的起點

列出開始時的畫面、功能狀態及必要資料。只保留會影響操作或判定的條件。

例如到期後免費額度的測試，要寫明訂閱有效、已有 3 個帳戶與 7 個類別，以及需比對的交易和餘額。取消購買若不涉及額度，就不要求先建這些資料。

沿用前一項時引用明確終點，仍寫出本項需要的狀態。獨立執行時從相同準備方式重建，不讓讀者猜測前文。

## 3. 寫明準備內容與完成條件

每項準備都要說明要建立什麼狀態，以及如何確認完成。例如「商店沒有有效訂閱，設定頁可見升級入口」。只寫設定完成或 build 成功不足以代表能開始。

操作說明保留會影響下一步的交接，例如「取得訂閱已到期的證據後，再返回 App」。命令、設定檔、日誌標記及清理方式放在執行說明，並從準備項目連過去。

準備需求不固定綁定人。由本次執行安排指定負責者，並由接手者核對完成條件。

## 4. 依畫面名稱寫操作

用打開、點選、輸入、取消、返回等具體動詞。寫出實際畫面與按鈕名稱，輸入資料使用具體值或可定位的測試資料引用。

例如「打開設定 → 點『升級至 Premium』→ 選月費 → 點『立即升級』」。不要只寫驗證訂閱或確認正常。

步驟按順序排列。遇到分支、等待、交接或需要立即取證的狀態，就拆成獨立步驟。機器步驟表仍遵守一列一個動作。畫面名稱不確定時先查規格或目前候選，不自行補造。

## 5. 為關鍵操作配上可觀察結果

每個會改變狀態或決定是否通過的操作，都要有對應結果。寫出應出現的文字、數量、金額、是否可以完成操作，以及應保留的資料。

需要前後比對時，先取得比對基準。需要確認沒有出錯時，寫出觀察區間與完成點。例如從取消購買至回到設定頁，不出現購買失敗提示，且升級入口仍可再次打開。

畫面能證明的結果使用畫面證據。商店到期、資料落庫等畫面不能單獨證明的結果，另列必要的系統證據與取得時點。誰取得證據由本次安排決定，不因改由 AI 操作或使用者操作就刪除必要證據。

規格有時限就引用時限。沒有時限時不憑空新增秒數作為產品驗收標準。準備未完成或證據缺少時，明列未驗證部分，不推定通過。

## 6. 交代結束後留下什麼

寫出完成後的畫面、功能狀態、保留資料及需要移除的測試資料。清理要指定對象，避免「清掉資料」這類不明確指令。

說明下一項能否直接接續，以及仍須補哪些準備。功能結果與清理結果分開記錄。清理失敗不能改寫已取得的功能結果，也不能當成下一項起點已成立。

## 測項、執行說明與本次安排

| 內容 | 放置位置 |
| --- | --- |
| 目的、起點、準備完成條件、操作、預期、必要證據、終點 | 可重用測項。使用不指定操作者的句子。 |
| 建置、模擬商店控制、資料準備、取證及清理的具體方法 | 執行說明與能力契約。從測項引用。 |
| 本次誰準備、誰操作、誰取證、哪裡停下供檢視、實際結果 | 目前 session。承接使用者選擇及已確認能力。 |

執行說明的環境生命週期仍由既有能力負責。`test-define` 維護定義，`test-run` 協調與判定，`test-ios` 管理 Simulator 環境。人或 AI 的操作分配不改變這些責任。

本次安排遵循下列原則。

- 在已授權範圍內，AI 承接已確認有能力完成的工作。能力以目前平台及工具可用性判斷，不以模型名稱推定。
- 使用者可以選擇自行操作，或只在指定結果出現時觀看。同一份測項保留相同預期與必要證據。
- 選擇在本輪持續有效。可套用整場或指定步驟，不逐步重問。
- 中途接手先交代目前畫面、已完成步驟、現有資料及下一步。同一時間只有一個 UI 操作者。
- 缺能力時只調整受影響步驟。沒有取得必要證據的部分維持未驗證。
- 操作、證據取得與使用者體驗評價可以由不同對象負責。客觀通過結果與使用者的主觀接受分開記錄。

對話可依本次安排使用「我」與「你」。可重用的測項不把這些人稱或特定 AI 名稱寫成固定責任。

## 改寫與審查

先核對現有規格、畫面名稱、測試資料及檢查點，再依六項要求補足內容。既有測項 ID、規格映射與場次引用需保留。拆分情境時逐一承接原檢查點，不因文字變簡單而縮減覆蓋。

審查時實際按文字推演。接手者應能定位起點，知道下一個動作，並從列出的證據判定結果。再檢查由 AI 或使用者操作時，是否都能沿用同一份定義。

本方法規範內容寫法。[計劃格式](plan_format.md)與[場次格式](run_script_format.md)仍持有 metadata 和機器欄位。導入中性角色欄位時須同步調整能力契約與檢核器，不能只替換欄位名稱。本內容範本不宣告既有執行器已支援新的分工方式。
